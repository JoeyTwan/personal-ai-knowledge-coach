# 产品验收报告 · 第一轮（静态验收）

> 验收目标：9 个核心闭环的 AI 行为是否符合产品理念
> 验收方式：代码逐行审查 + prompt 审查（本轮未做真实 LLM 调用）
> 验收时间：2026-09-04
> 验收结论：**发现 5 个 P0 级确定性缺陷、4 个 P1 级重要缺陷、8 个 P2 级体验缺陷；真实 AI 输出需填 Key 后二次验证**

---

## 〇、关键阻塞项（必须先解决）

| 阻塞项 | 现状 | 影响 |
| --- | --- | --- |
| DeepSeek Key 为空 | `.env` 中 `DEEPSEEK_API_KEY=` 长度为 0 | 所有 AI 接口（共创/问答/出题/评估/画像/断层/合并）直接抛「未配置 KEY」，无法产出真实 AI 输出 |

**本轮验收的边界说明**：
- 「实际行为」一栏，凡标注【代码确定】的，是读代码即可确认的确定性行为，无需等 Key；
- 凡标注【待 Key 验证】的，是 prompt 设计层面的推断，需要填 Key 后真实调用才能下最终结论。

## 一、九个闭环 + 三个专项能力的测试案例

> 测试案例的输入均采用贴合用户（华为鲲鹏/昇腾销售）的真实业务场景，用于同时检验「职业差异深度」能力。

### 用例 1 · 知识共创

| 字段 | 内容 |
| --- | --- |
| **输入** | 用户：「我今天学了视觉 Transformer，它最大的优势是一次能看整张图，比 CNN 强。」 |
| **预期行为（产品理念）** | AI 识别这是「观点/学习结论」，主动追问澄清（如「你指相比 CNN 的局部感受野，ViT 在全局关系建模上更强吗」），不机械总结，多轮讨论达成共识后才输出可确认的结构化草稿，并自动分类。 |
| **实际行为** | 【代码确定】`classifySystem`（自动分类）是死代码，`confirmKnowledge` 和 `createKnowledge` 均不调用它，入库知识 category 为 null。共识草稿由 `cocreateSystem` 直接在 `<CONSENSUS>` 标记里输出。【待 Key 验证】prompt 只写了「主动追问」，没有「至少追问 N 轮」硬约束，AI 可能第一轮就输出共识标记，退化成机械总结。共识标记解析依赖精确的 `<CONSENSUS>...</CONSENSUS>` 格式，格式稍有偏差则草稿字段丢失。 |
| **问题** | ① 自动分类未接线；② 无追问轮次约束，可能一轮共识；③ 共识标记格式脆弱 |
| **严重程度** | P0（分类缺失）、P2（追问约束、格式脆弱） |
| **修改建议** | ① 在 `confirmKnowledge` 入库前调用 `classifySystem` 生成 `categoryPath`；② 在 `cocreateSystem` prompt 增加「首次输入必须先追问至少 1 个澄清问题，不要立即给出共识」的强制规则；③ `parseConsensus` 增加容错（允许代码块包裹、允许首尾多余文本）。 |

### 用例 2 · 知识关联（含「知识桥梁」专项）

| 字段 | 内容 |
| --- | --- |
| **输入** | 知识库已有「Transformer 是什么」「什么是 Attention」，新录入「ViT 把图像切成 patch 当作 token 处理」。 |
| **预期行为（产品理念）** | AI 发现新知识与旧知识的关系（上位/下位/前置/应用），并且当 A 与 B 之间缺关键中间知识 C 时，能识别出「知识桥梁」并提示用户补 C。 |
| **实际行为** | 【代码确定】关系发现用 `others.find(o => o.title === s.toTitle)` 精确匹配标题，AI 返回的标题只要与库内标题有细微差异（多一个字、改说法），关系就静默丢弃。`bridge` 关系被当作一条普通 `KnowledgeRelation` 存，但「桥梁知识 C」本身是缺失的、不存在的节点，无法用 from/to 两个已有节点表达，因此 bridge 实际上存不下正确语义。 |
| **问题** | ① 标题精确匹配导致关系大量丢失；② 知识桥梁数据结构无法承载「缺失的 C」，与「知识断层」功能割裂 |
| **严重程度** | P0（桥梁不可用）、P1（标题匹配） |
| **修改建议** | ① 关系发现 prompt 让 AI 返回目标知识的 `id`（或同时给标题+匹配容错），代码用 id 匹配、标题做模糊回退；② 把「知识桥梁」统一到 `KnowledgeGap` 体系：A 与 B 之间缺 C 时生成一条 `bridge` 类型的 gap（`fromKnowledgeId`=A、`toKnowledgeId`=B、`gapDescription`=C），不再用 relation 表达。 |

### 用例 3 · 知识调用（Ask）

| 字段 | 内容 |
| --- | --- |
| **输入** | 「客户需要一个 AI 服务器整机集成方案，我以前记录过合适的公司吗？」 |
| **预期行为（产品理念）** | 优先检索知识库，找到历史记录的「XX 公司」相关知识，回答时说明「你在 X 时间记录过…」，并明确区分「知识库已有」和「AI 补充」。 |
| **实际行为** | 【代码确定】检索是纯 `contains` 关键词匹配：`tokenize` 只按标点切分，中文句子无分词，整句往往变成一个 token 去匹配标题/结论/详情，召回率极低；无匹配时退回「最近 10 条」任意知识。【待 Key 验证】「区分已有/补充」只靠 `askSystem` prompt 口头要求，无结构化约束，AI 可能不标注或标注混乱。 |
| **问题** | ① 检索无分词、非语义，核心「过去知识帮助现在」闭环召回差；② 已有/补充区分无结构化保证 |
| **严重程度** | P0（检索）、P1（区分标注） |
| **修改建议** | ① 引入分词（可用开源 `nodejieba` 或 `@node-rs/jieba`）＋ 向量检索（嵌入存 SQLite，复用成熟库），先做「关键词＋向量」混合召回；② `askSystem` 要求 AI 用固定标记输出，如 `【知识库已有】…【AI 补充】…`，并在代码层校验。 |

### 用例 4 · 复习出题（含「题型动态变化」专项）

| 字段 | 内容 |
| --- | --- |
| **输入** | 用户点击「开始复习」，进入会话，依次答题。 |
| **预期行为（产品理念）** | 题目难度根据用户当前掌握度动态变化：答对升级（回忆→理解→关联→应用），答错降级并回到原知识解释后重测；8 类题型都会被按需使用。 |
| **实际行为** | 【代码确定】`chooseQuestionType` 完全按 `reviewCount` 机械递增（0→recall、1→understanding、2→comparison、3→association、4+→application），完全不看 `state` 各维度、不看上一题对错，答错也不会降难度。8 类题型中 `counterexample`（辨析）、`open`（开放）、`choice`（选择）从不被调度，实际只用 5 类。 |
| **问题** | ① 难度非「动态」而是「轮换」；② 答错不降级，违背需求 19；③ 题型覆盖不全 |
| **严重程度** | P1 |
| **修改建议** | ① `chooseQuestionType` 改为读 `state` 各维度：低 `understanding` 出理解题、低 `application` 出应用题、答错后先出低难度题并附带解释；② 增加 choice 作为「认知体检」入口、counterexample 作为「真的会 vs 看过」的判别题型。 |

### 用例 5 · 掌握度评估（含「真的会 vs 只是看过」专项）

| 字段 | 内容 |
| --- | --- |
| **输入** | 用户对「Transformer 为什么需要算力」作答，系统评估并更新掌握状态。 |
| **预期行为（产品理念）** | 不只判断「对/错」，还要区分「背下来」和「真理解/会应用」；记录「为什么可能答错」（遗忘/混淆/断层/误用），并据此制定不同复习方式。 |
| **实际行为** | 【代码确定】评估输出有 `errorType` 字段（遗忘/混淆/关系缺失/前置不足/误解/误用），但 `updateStateAfterAnswer` 只做数值加减：`score>=0.7` 就算对，答对统一加 recall，维度映射粗糙（comparison 和 association 都映射到 association）。没有「背诵 vs 理解」的判别机制，`errorType` 存了但**不用于差异化复习策略**（错误归因闭环断裂）。 |
| **问题** | ① 「真的会 vs 看过」无判别；② errorType 存而不用，错题归因闭环断裂 |
| **严重程度** | P0 |
| **修改建议** | ① 用「辨析题/反例题」来判别真理解：用户能指出一个错误说法的漏洞，才说明真懂，不能只看回忆题答对；② 让 `errorType` 驱动下一次出题类型（遗忘→延长间隔再考、混淆→出对比题、断层→推荐中间知识、误用→出场景题）。 |

### 用例 6 · 知识断层（含「职业差异深度」专项）

| 字段 | 内容 |
| --- | --- |
| **输入** | 知识库有「GPU 是什么」（A）和「AI 服务器整机方案」（D），中间缺「显存与算力的关系」（C）。用户是销售。 |
| **预期行为（产品理念）** | AI 识别 A→D 之间缺 C，并**结合职业判断**：销售只需理解「显存影响服务器成本和适用场景」的概念层，无需深入 CUDA 数学；给出「值得学，但学概念即可」的个性化建议。 |
| **实际行为** | 【代码确定】`gapSystem` prompt 写了「结合画像判断」，但 `getProfileText` 只注入 occupation/workDomain/currentFocus/technicalDepth/businessLevel/primaryKnowledgeAreas/learningGoals 7 个字段，**不注入 deepDiveAreas（倾向深入）和 shallowAreas（只需了解）**，而这两个字段恰恰是「哪些只需概念、哪些要深入」的判断依据。画像推断阶段也无行为数据支撑这两个字段。 |
| **问题** | ① 判断「断层是否值得学/学多深」的关键字段没进 prompt；② 断层发现需手动触发（POST /api/gaps/discover） |
| **严重程度** | P0（职业深度个性化不可用）、P2（手动触发） |
| **修改建议** | ① `getProfileText` 增加 deepDiveAreas、shallowAreas、commonMistakes、weakDirections；② 断层发现接入「新知识入库后」自动触发（异步、失败静默即可）。 |

### 用例 7 · 知识合并

| 字段 | 内容 |
| --- | --- |
| **输入** | 知识库存在 3 条：「XX 公司能做液冷」「XX 公司有液冷团队」「XX 公司最近做过液冷项目」。 |
| **预期行为（产品理念）** | AI 识别这 3 条是同一知识对象，建议合并；用户确认后生成一条更完整的知识，旧知识归档保留历史，并建立演化关系。 |
| **实际行为** | 【代码确定】`detectDuplicates` 用 id 匹配（可靠）；`mergeKnowledge` 合并后归档旧知识并建 `evolution` 关系（正确）。但合并生成的新知识**不重新调用 `discoverRelations`**，导致新知识在知识图谱中孤立。 |
| **问题** | ① 合并后新知识不重建关系，图谱断裂 |
| **严重程度** | P1 |
| **修改建议** | `mergeKnowledge` 生成新知识后，调用 `discoverRelations` 重建与新知识的关联。 |

### 用例 8 · 知识演化

| 字段 | 内容 |
| --- | --- |
| **输入** | 场景：7 月「听说 XX 能做液冷」→ 8 月「客户反馈 XX 在做液冷」→ 9 月「项目验证 XX 液冷」。 |
| **预期行为（产品理念）** | AI 把三次输入识别为**同一条知识随时间的可信度增强**，更新现有知识对象的演化状态，保留历史，可信度逐步提升，不生成 3 条重复知识。 |
| **实际行为** | 【代码确定】演化只在用户**手动调用** `updateKnowledge` 且核心结论变化时保存 `KnowledgeVersion`。录入新知识时（`createKnowledge` / `confirmKnowledge`）**没有 AI 判断「这是否是已有知识的更新」**，需求第 12 条的案例 E（知识演化）端到端未实现。 |
| **问题** | ① 无 AI 驱动的演化识别，新输入会生成重复知识；② 版本变化原因固定写「内容更新」，无来源/可信度变化记录 |
| **严重程度** | P0 |
| **修改建议** | 共创入库时增加一步：AI 判断当前共识是否是对某条已有知识的更新/增强，若是则走「更新旧知识 + 记录版本 + 提升 confidence + 来源追加」，否则新建。 |

### 用例 9 · 用户画像

| 字段 | 内容 |
| --- | --- |
| **输入** | 用户已积累若干销售相关知识与若干次答题记录，触发画像刷新。 |
| **预期行为（产品理念）** | 系统从长期使用中自动推断职业、技术深度、兴趣、常犯错误、薄弱方向，且随使用自动变化，无需用户填问卷。 |
| **实际行为** | 【代码确定】`refreshProfile` 的输入**只有知识内容**（title/type/tags/coreConclusion），完全没有答题表现、错误类型等行为数据；`inferProfileSystem` 输出的 `commonMistakes`、`weakDirections` 字段因此无法被真实推断（只能瞎猜或留空）。画像刷新需手动 POST /api/profile/refresh，无任何自动触发。 |
| **问题** | ① 画像无行为数据源，常犯错误/薄弱方向形同虚设；② 画像不会自动更新 |
| **严重程度** | P1（行为数据缺失）、P2（自动更新） |
| **修改建议** | ① 画像输入加入答题统计（各维度得分、errorType 分布、reviewCount）；② 在答题提交、知识入库后异步触发画像增量更新。 |

## 二、三个专项能力的总结论

| 专项能力 | 验收结论 | 根因 | 严重程度 |
| --- | --- | --- | --- |
| **知识桥梁** | ❌ 不可用 | bridge 被当成普通 relation 存，「缺失的中间知识 C」无节点可承载；与断层割裂 | P0 |
| **职业差异深度** | ❌ 不可用 | 判断「学多深」的关键字段 deepDiveAreas/shallowAreas 未注入 prompt，且画像阶段无数据支撑 | P0 |
| **真的会 vs 只是看过** | ❌ 不可用 | 掌握度纯数值加分，无辨析/反例题判别机制；errorType 存而不用，错题归因闭环断裂 | P0 |

## 三、缺陷汇总（按严重程度）

### P0（核心能力缺失 / 严重错误，共 5 个）

| # | 缺陷 | 位置 |
| --- | --- | --- |
| P0-1 | AI 自动分类未接线（`classifySystem` 死代码），知识入库无分类 | cocreation.service / knowledge.service |
| P0-2 | 知识检索无分词、非语义，`contains` 关键词匹配召回率极低 | recall.service.ts `tokenize` |
| P0-3 | 知识桥梁数据结构无法承载「缺失的 C」，与断层割裂 | relation.service / schema |
| P0-4 | 知识演化无 AI 驱动，新输入会生成重复知识 | cocreation.service / knowledge.service |
| P0-5 | 「真的会 vs 看过」无判别机制，errorType 存而不用 | coach.service `updateStateAfterAnswer` |

### P1（重要缺陷，共 4 个）

| # | 缺陷 | 位置 |
| --- | --- | --- |
| P1-1 | 题型硬编码轮换，不看掌握状态、答错不降难度 | coach.service `chooseQuestionType` |
| P1-2 | 关系匹配用标题精确匹配，关系大量静默丢失 | relation.service `discoverRelations` |
| P1-3 | 画像关键字段（deepDiveAreas/shallowAreas）未注入 prompt | user.service `getProfileText` |
| P1-4 | 画像无行为数据源，commonMistakes/weakDirections 无法推断 | profile.service `refreshProfile` |

### P2（体验 / 健壮性，共 8 个）

| # | 缺陷 |
| --- | --- |
| P2-1 | 共创无「至少追问 N 轮」约束，可能一轮共识 |
| P2-2 | 共识标记 `<CONSENSUS>` 解析无容错 |
| P2-3 | `extractKnowledgeSystem` 也是死代码（未接线） |
| P2-4 | Ask 无匹配时退回最近 10 条任意知识，可能误导 |
| P2-5 | 「已有/补充」区分无结构化约束 |
| P2-6 | 合并后新知识不重建关系 |
| P2-7 | 8 类题型只调度 5 类，辨析/开放/选择从不出现 |
| P2-8 | 关系发现、断层、画像、推荐均需手动触发或失败静默 |
